From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives: every step a wallet such as MetaMask performs, implemented on this page, followed by the statistical properties of each step.

01

Homework

Every step except the first is deterministic, so the same words always give the same addresses in every wallet. This is why a 12-word backup is enough to restore a whole wallet. Every step also goes one way only: an address does not reveal the public key, the public key does not reveal the private key, and a child key does not reveal the seed.

04

Role and purpose of each standard

BIP-39 mnemonic & seed

Role: turns random entropy into words a human can write down, and turns those words into a binary seed.

How: 128 bits of entropy plus 4 checksum bits (the first bits of its SHA-256) are split into twelve 11-bit numbers, and each picks one of 2048 words. The seed is PBKDF2-HMAC-SHA512 of the sentence, with salt "mnemonic" + passphrase, over 2048 iterations.

Why: backups people can copy reliably, typo detection through the checksum, and a deliberately slow KDF that makes guessing harder. The optional passphrase creates a completely different wallet from the same words.

BIP-32 HD key derivation

Role: derives an unlimited tree of key pairs from one seed.

How: the master key and chain code are HMAC-SHA512("Bitcoin seed", seed). Each child is HMAC-SHA512(chain code, data ‖ index), and its left half is added to the parent key mod n. Hardened children (index ≥ 2³¹, written with ') use the parent private key as input. Normal children use the parent public key, so a watch-only wallet can derive child public keys without any secret.

Why: a new address for every account or payment with one single backup, and branches that cannot be traced back to the parent.

BIP-44 derivation paths

Role: fixes where in the BIP-32 tree each coin and account lives, so different wallets agree.

How: m / purpose' / coin_type' / account' / change / address_index. For Ethereum: purpose 44', coin type 60' (SLIP-44), so the first address is m/44'/60'/0'/0/0.

Why: interoperability. Restore your words in another app and it looks in the same places. A wallet using a different path finds different (empty) addresses.

secp256k1 public-key cryptography

Role: links the private key to the public key and makes signatures possible.

How: public key Q = k·G on the curve y² = x³ + 7 over a 256-bit prime field, the same scalar multiplication as Homework 1. Transactions are signed with ECDSA, and the network recovers Q from the signature.

Why: computing k·G is fast, while recovering k from Q (ECDLP) needs about 2¹²⁸ operations. Anyone can verify a signature, but only the key owner can produce it.

Keccak-256 address hash

Role: compresses the 64-byte public key into a short, fixed-size identifier.

How: address = last 20 bytes of Keccak-256(x ‖ y). Ethereum uses the original Keccak submission, whose padding differs from the later FIPS-202 "SHA3-256", so the two give different outputs. This page implements Keccak from scratch and also checks the SHA3 variant against OpenSSL.

Why: shorter addresses, a uniform-looking output, and an extra layer of protection, because the public key stays hidden until the first transaction is signed.

EIP-55 checksum encoding

Role: detects typos in addresses without changing their format.

How: hash the lowercase hex address with Keccak-256. Each letter a–f is written in upper case if the matching hex digit of the hash is ≥ 8.

Why: backward compatible, since all-lowercase addresses remain valid. An address has about 15 letters on average, so a random typo goes undetected with probability ≈ 2⁻¹⁵. It is an encoding, not encryption: it hides nothing.

05

Distinguishing the primitives

The pipeline combines five different kinds of operation. They are easy to confuse, but each has a different job:

CategoryWhere in the pipelineSecret involved?Reversible?Purpose
Key generation128–256 random bits (BIP-39 entropy)Creates the secret—The only source of unpredictability in the whole wallet
Key derivationPBKDF2-HMAC-SHA512 (seed); HMAC-SHA512 tree (BIP-32, paths from BIP-44)Yes: words, passphrase, chain codeNoTurn one secret into many independent secrets, deterministically
Public-key cryptographysecp256k1: Q = k·G, ECDSA signaturesPrivate key kNo (ECDLP)Prove ownership; let others verify without knowing k
HashingKeccak-256(public key) → address; SHA-256 inside the BIP-39 checksumNoNo: one-wayFixed-size, uniform-looking fingerprint of data
ChecksumsBIP-39 checksum bits, EIP-55 case patternNo—Detect accidental errors (typos), not attacks
EncodingBits → words (BIP-39), bytes → hex, hex → mixed case (EIP-55)NoYes, triviallyRepresent data in a form humans and software can handle

Key generation and key derivation differ in an important way. Generation needs real randomness and happens once. Derivation is deterministic and can be repeated any number of times, which is what makes backups and multiple accounts possible. Checksums and encodings provide no secrecy: anyone can compute and reverse them. Nothing in this pipeline is encryption either, since no data is hidden and later revealed with a key.

How the steps fit together

Each step's output is the next step's input, and each step goes one way only. Random entropy is encoded as words with a checksum, so a person can back it up safely. A slow key derivation turns the words into a seed, and a second, fast key derivation expands the seed into a tree of private keys at standard paths. Public-key cryptography turns each private key into a public key that can verify signatures. Hashing shortens that public key into an address. Finally, an encoding with a checksum protects the address against typos. Compromising any later stage (an address, a public key, even a child key) does not reveal the stages before it.

06

Historical context

The wallet pipeline stacks almost forty years of cryptography. The general-purpose building blocks came first, and the wallet-specific standards were designed on top of them once Bitcoin and Ethereum needed them.

  1. 1977
    RSA: the first widely used public-key cryptosystem (Rivest, Shamir, Adleman), based on the difficulty of factoring. It established the idea of a public/private key pair.
  2. 1985
    Context: elliptic-curve cryptography proposed independently by Koblitz and Miller. It offers the same security as RSA with much shorter keys.
  3. 2001
    SHA-2 family (SHA-256, SHA-512): standardized by NIST. It uses the Merkle–Damgård construction. SHA-256 appears in the BIP-39 checksum, and SHA-512 inside HMAC/PBKDF2 for the seed and BIP-32.
  4. 2009
    Context: Bitcoin launches, using secp256k1 (from the SEC 2 curve list) and SHA-256.
  5. 2012
    BIP-32: hierarchical deterministic wallets, one seed for a whole tree of keys. In the same year Keccak won NIST's SHA-3 competition.
  6. 2013
    BIP-39: mnemonic code, i.e. the seed as human-readable words.
  7. 2014
    BIP-44: a standard path layout for multiple coins and accounts in one HD tree.
  8. 2015
    SHA-3 standardized by NIST (FIPS 202), based on Keccak but with a different padding. Ethereum launched the same year using the original Keccak padding, so its "Keccak-256" is not the final SHA3-256.
  9. 2016
    EIP-55: mixed-case checksum for Ethereum addresses, added because plain hex addresses had no error detection.

The order explains the design. Ethereum reused existing, well-studied primitives (ECC, SHA-2, Keccak) and existing Bitcoin wallet standards (BIP-32/39/44), and added only what was missing: a checksum for its addresses.

Both are cryptographic hash functions with the same goals (preimage, second-preimage and collision resistance, plus random-looking output), but they are completely different designs. SHA-3 was chosen as a backup built on different principles, so that a breakthrough against SHA-2 would not break both.

Keccak-256 ≠ SHA3-256. When NIST standardized Keccak as SHA-3, it changed the padding byte from 0x01 to 0x06, adding domain-separation bits. Ethereum had already adopted the original Keccak, so the two functions use the same permutation but give completely different outputs:

Why several techniques instead of one?

Each step needs a different property, and no single algorithm provides all of them:

  • BIP-39 / BIP-32 / BIP-44: key management and derivation. These need determinism and structure: the same words must rebuild the same keys in any wallet, and one seed must expand into many unrelated keys at agreed locations. A hash or a signature scheme cannot organize keys into a tree. These standards are protocols built from HMAC and PBKDF2.
  • secp256k1: public/private key relationship and signatures. This needs an asymmetric, algebraic relation: a public key anyone can use to verify, linked to a private key only the owner has. Hash functions have no such structure. As Homework 1 showed, this structure is exactly what makes signatures possible.
  • Keccak-256: hashing. This needs compression and randomness: a short, fixed-length, uniform-looking identifier, with no algebraic structure that an attacker could exploit. The elliptic curve is the wrong tool here precisely because it is structured.
  • EIP-55: checksum and error detection. This needs backward-compatible error detection at zero cost in length. It protects against human mistakes, not attackers, so it only needs to be simple and compatible.

Splitting the work also means each piece can be analysed, replaced or upgraded on its own (Bitcoin added Schnorr signatures without changing BIP-39), and that each relies on a separate, well-studied hardness assumption.

11

Conclusions

  • A wallet is a deterministic chain of one-way functions started by 128–256 bits of real randomness. That entropy is the only secret. Everything after it can be recomputed by anyone who has it.
  • Statistically, the hashed and derived outputs (seed, child keys, Keccak addresses) pass simple randomness tests: balanced bits, about 50% avalanche, and uniform word and value frequencies. These are exactly the hash-function properties discussed in Homework 1.
  • The checksums are statistical too: a random 12-word sentence is valid with probability 1/16, and a random EIP-55 typo slips through with probability about 2⁻¹⁵. They detect accidents, not attacks.
  • Security fails where randomness fails: weak entropy at the start (a predictable generator, or words chosen by a person) reduces the 2¹²⁸ search to something feasible, however strong the later steps are.
